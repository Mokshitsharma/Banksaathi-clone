## Data model

Source: `services/api/prisma/schema.prisma`, plus raw SQL added to the `init` migration. There are three migrations:
`20260925103418_init`, `20260925113747_commission_rule_offer_copy`, and `20260925125429_security_hardening`.
Every id is a UUID generated by Prisma (`@default(uuid()) @db.Uuid`). **All money columns are 32-bit `INTEGER` paise.**

### Enums
- `Role`: affiliate, admin
- `KycStatus`: unverified, pending, verified, rejected
- `ProductType`: loan, credit_card, insurance
- `LeadStatus`: new, contacted, in_progress, converted, rejected
- `CommissionType`: flat, percent
- `CommissionStatus`: pending, approved, paid, rejected
- `PayoutStatus`: pending, processing, completed, failed
- `LedgerType`: commission_credit, payout_debit, payout_reversal
- `KycDocumentType`: pan_card, bank_proof, other

### `commissions`
id, leadId → leads, userId → users, ruleId → commission_rules (**SET NULL** if the rule is deleted), tier,
amountPaise (int, **CHECK > 0**), status (CommissionStatus, default pending), createdAt, updatedAt.
Unique (lead_id, user_id, tier); index (user_id, status).

### `payouts`
id, userId → users, amountPaise (int, **CHECK > 0**), status (PayoutStatus, default pending), payoutMethod (text, set to
`bank_transfer:<masked account>`), transactionRef?, failureReason?, createdAt, updatedAt. Indexes (user_id, status) and (status).

### `ledger_entries` (append-only)
id, userId → users, type (LedgerType), amountPaise (signed: credits positive, debits negative), balanceAfterPaise
(**CHECK ≥ 0**), referenceId (uuid of the commission or payout), description?, createdAt.
Unique (type, reference_id), so the same commission can't be credited twice. Index (user_id, created_at).
**Trigger `ledger_entries_no_update_delete` raises an exception on any UPDATE or DELETE.**

### `device_tokens`
id, userId → users (cascade), token (unique), platform (android | ios | web, validated by the API), createdAt, updatedAt.

## Business rules enforced on the server

| Rule | Where it's enforced |
|---|---|
| **Balance is computed from the ledger, not stored as a mutable column.** `getBalance()` = `SUM(amount_paise)` over the user's `ledger_entries`. There is no balance column on `users`. Each ledger row also stores a `balanceAfterPaise` snapshot, which is written once and never updated. | `modules/ledger/ledger.service.ts` |
| Ledger is append-only: a DB trigger rejects UPDATE and DELETE. Balance can never go below zero (CHECK constraint plus an application check). | init migration SQL, `appendLedgerEntry()` |
| Ledger writes are serialised per user with `SELECT … FOR UPDATE` on the user row. Payouts lock the row **before** inserting, to avoid FK-lock upgrade deadlocks. | `lockUser()`, `appendLedgerEntry()`, `requestPayout()` |
| The same commission or payout can't be booked twice: `UNIQUE(type, reference_id)` on the ledger, and `UNIQUE(lead_id, user_id, tier)` on commissions. | schema |
| Lead pipeline: new → contacted → in_progress → converted; rejected is reachable from any open state. Converted and rejected are terminal. Uses an optimistic check (`updateMany where status = previous`). | `LEAD_TRANSITIONS`, `updateLeadStatus()` in `modules/leads/lead.service.ts` |
| On conversion, one **pending** commission is created per active rule for the product. Tier *n* pays the *n*-th person up the `referredBy` chain (tier 1 = the lead's referrer). Flat rules pay `value` paise; percent rules pay `floor(deal × bp / 10000)`. **The deal amount must be supplied by the admin at conversion**; the affiliate's estimate is ignored. | `createCommissionsForLead()`, `calculateAmount()` in `modules/commissions/commission.engine.ts` |
| Approving a commission credits the ledger (`commission_credit`). Only pending commissions can be approved or rejected. | `approveCommission()`, `rejectCommission()` |
| **KYC gating:** a payout request requires `kycStatus = verified` (403 otherwise) and at least `MIN_PAYOUT_PAISE`. The amount is debited from the ledger immediately (`payout_debit`). | `requestPayout()` in `modules/payouts/payout.service.ts` |
| Payout states: pending → processing → completed, and pending or processing → failed. A failure writes a `payout_reversal` credit. Completion marks the oldest approved commissions as `paid`, up to the total paid out. | `markProcessing/markCompleted/markFailed`, `settleCommissions()` |
| KYC: once Aadhaar, PAN and bank are all verified, the status moves to `pending` for review. While pending or verified, the verification steps are locked (409); document uploads are still allowed while pending. An admin approval requires all three flags. Rejection clears all three flags. | `modules/kyc/kyc.service.ts` |
| Raw Aadhaar is never persisted. PAN and account numbers are stored encrypted, and only masked values are ever returned. | `kyc.routes.ts`, `kyc.service.ts` |
| A single money amount is capped at ₹2,00,00,000 so it can't overflow the INT4 columns. | `MAX_AMOUNT_RUPEES` in `src/lib/http.ts` |
